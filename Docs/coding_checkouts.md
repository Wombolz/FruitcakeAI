# Managed Coding Checkouts

Follow-on: [Coding Workspace Lifecycle](coding_workspace_lifecycle.md) adds
migration 056, reusable checkout attachments, model/session controls, reviewed
local commits, and operator-only fast-forward delivery. It supersedes the original
one-session and fixed-HEAD restrictions described below.

## Scope

This slice implements disposable Git worktree identity, committed baselines, lifecycle/recovery, runtime routing, and explicit clean-only removal. It deliberately does **not** enable edit/write tools, shell commands, package installation, remote Git, automatic commits, merges, or publishing. Read-only refers to the allowed runtime tools, not a read-only mount or OS sandbox. This remains a trusted-local alpha.

A session can inspect its explicitly authorized source repository and later explicitly attach one managed checkout while idle or interrupted, including after read-only run history. The transition retires any retained source runtime before attaching the checkout, preserves conversation history, and starts the next run in a fresh runtime/context generation at the managed path. Earlier excerpts are context, not current file observations; the runtime is told to reread files in its current workspace. Once attached, the session never silently falls back to the source path, including after failure or removal. Projects remain organizational, not filesystem grants.

## Storage And Lifecycle

Managed paths are generated by the backend under `<storage_dir>/coding_checkouts/<user-id>/<checkout-id>`. Users cannot supply a destination, branch/ref, or commit through the API. The managed root and owner directories must be canonical, private (0700), and owned by the backend operator; unsafe pre-existing directories are refused, not silently chmodded/reused. Worktree destinations must not already exist. The checkout UUID and expected path are checked before use.

Migration 053 records owner/session identity, canonical managed path, baseline commit, state, safe error code, and timestamps. The baseline is stored before checkout creation. The state machine is:

- `creating` -> `ready` or `failed`;
- `ready`/`failed`, with a closed session -> `removing` -> `removed`;
- dirty removal returns to `ready` with `checkout_dirty`, preserving reviewability;
- interrupted creation/removal becomes `failed`, retaining its identity and any filesystem/Git registration for explicit recovery.

Creation and removal return immediately with HTTP 202 and run as bounded background jobs. Requests are idempotent by session identity: a repeated creation returns the existing record instead of duplicating a checkout. Two provisioning/removal jobs can run at once; at most eight non-removed checkout records are retained per owner, including failures. These are count/time bounds, not a disk quota or hostile-repository containment guarantee.

Checkout creation/removal has a 60-second operation deadline, baseline lookup 15 seconds, and validation 15 seconds, with bounded Git output and cleanup intervals. Stop/approval handling does not hold a lock over checkout Git operations. Grant revocation cancels matching jobs; shutdown cancels/reaps jobs and durably finalizes unstarted reservations too. Startup marks abandoned `creating`/`removing` records `failed/backend_restart`; it never resumes mutation or deletes files automatically.

A failed operation may leave a partial directory or locked Git registration. Keep its durable record for operator inspection. Clean, valid retained worktrees can be removed explicitly after closing the session; a failed pre-check that created/registered nothing can also be marked removed safely. Missing-but-still-registered, altered-baseline, replaced, or otherwise invalid checkouts require operator recovery. No destructive cleanup workaround is inferred. Database downgrade drops metadata only and never deletes filesystem content; preserve ownership records before downgrading.

## Git And Execution Boundary

All Git calls use fixed command forms/argument arrays and a minimal environment. Pager, optional index-refresh locks, hooks, fsmonitor, untracked cache, external diff/textconv, lazy fetching, Git transports, and submodule recursion are disabled. Repository-local clean/smudge/process filters (including required filters) are explicitly neutralized for status, diff, and checkout population; this also hardens the earlier repository-review path. Filter expansion is bounded. Filter-dependent assets such as Git LFS remain committed pointers, not downloaded files.

Ready worktrees must still be canonical directories with a regular `.git` indirection, the expected common Git directory, detached HEAD, and the original baseline commit. Validation runs before every coding prompt and before/after repository inspection. A modified HEAD, missing/replaced path, changed storage root, inactive grant, or invalid managed identity fails closed. Dirty source edits are never imported implicitly. Clean-only removal checks ignored files too and uses ordinary Git removal without force.

The guard and path checks remain application-level defenses for operator-controlled repositories/runtimes. They do not prevent a compromised process or hostile concurrent filesystem writer from bypassing hooks/racing checks. Disabling Git helpers is not an OS/network sandbox. The model receives only its existing approved local-provider credential; Git receives no inherited Fruitcake/provider/Git credentials.

## HTTP And Client Rules

`GET /coding/status` adds `managed_checkouts: true` when this service supports provisioning. `mode` remains `read_only` and event schema stays 1. Old clients ignore the additive field; new clients hide provisioning on old backends that omit it.

- `GET /coding/sessions/{session_id}/checkout`: owner-scoped nullable checkout metadata.
- `POST /coding/sessions/{session_id}/checkout`: explicitly reserve/create the checkout for an idle/interrupted session, including one with source history; HTTP 202. Active and closed source sessions cannot transition. Existing checkout records remain the idempotency boundary.
- `POST /coding/sessions/{session_id}/checkout/remove`: explicitly remove a closed session's clean managed checkout; HTTP 202.

Responses contain `id`, `session_id`, `canonical_path`, nullable `baseline_commit`, `status`, and nullable `error_code`. Bodies do not accept arbitrary paths/refs. Existing coding auth, owner scoping (including operators), active-grant checks for mutations, no-store headers, and safe error envelopes apply. `checkout_conflict`, `checkout_unavailable`, and `checkout_invalid` are HTTP 409; existing capacity/unavailable errors also apply. A 202 is acceptance, not success: inspect durable status/error afterward.

The client performs at most 45 busy-status polls, with two seconds between reads and a bounded timeout per HTTP request. Leaving Code cancels only the observer, not provisioning. Refresh reconciles durable status. Late results cannot replace another session; a lost mutation response blocks submissions until status is reconciled. No checkout is implicitly created by selecting a session, loading the page, or submitting a prompt. Current right-inspector/top-diff/window layout and titlebar geometry are preserved.
